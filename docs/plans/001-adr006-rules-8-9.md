## Phase 1: Quota entries and one authoritative execute ceiling

Goal: every rule-8 resource limit is a visible per-stack property of the Compose runtime entry, and 300 seconds is the execute wall-clock ceiling in every stack on both sandbox paths.
Validation: `uv run --directory backend pytest tests/test_coding_tools.py tests/test_core.py -q` and `uv run --directory backend ruff check app tests` from the repository root.

Steps:
1. Move sandbox quotas onto the runtime allowlist entry — in `docker-compose.yml`, extend the `SANDBOXD_RUNTIMES` workspace entry (the rule-7 mechanism) with `mem_limit=${SANDBOX_MEM_LIMIT:-2g};cpus=${SANDBOX_CPUS:-2.0};pids_limit=${SANDBOX_PIDS_LIMIT:-512}` so the caps ride the entry and show up in `compose config` diffs; keep the service-wide `SANDBOXD_MEM_LIMIT`/`SANDBOXD_CPUS` as the backstop for non-runtime sessions, and extend the rule-7 mechanism comment to say the entry now carries quotas too (cite ADR-006 rule 8).
2. Size-bound the sandbox workspace root — give the `sandbox_workspaces` named volume tmpfs `driver_opts` with `size=${SANDBOX_WORKSPACE_SIZE:-4g}`; document in the volume comment the accepted tradeoff (tmpfs bytes vanish when sandboxd is recreated; the attach-time briefing's re-clone path recovers, same as after GC) and that the bound is a cap, not an allocation.
3. Make 300 seconds the authoritative execute ceiling — raise `SANDBOX_TIMEOUT_SECS` in `backend/app/core/config.py` from 60.0 to 300.0 to match sandboxd's service ceiling; set `SANDBOXD_EXECUTE_TIMEOUT: "300"` explicitly on the sandboxd service so both ends of the agreement are visible; keep dev's existing explicit pin; clamp the docker-backend path in `backend/app/agents/tools/coding.py` so a model-requested execute timeout never exceeds `settings.SANDBOX_TIMEOUT_SECS` (mirroring sandboxd's `command_timeout` clamp, which the remote path already gets).
4. Lock the timeout wiring with tests — extend `backend/tests/test_coding_tools.py`: the remote backend is constructed with `settings.SANDBOX_TIMEOUT_SECS`; the docker path clamps an oversized requested timeout; the settings default is 300.0.

## Phase 2: Sandbox-state garbage collection

Goal: idle sandbox state is reclaimed by a taskiq periodic task after a 7-day idle TTL, the `workspaces` row surviving collection.
Validation: `uv run --directory backend pytest tests/test_worker_taskiq.py tests/test_workspaces.py tests/test_coding_tools.py tests/test_migrations.py -q` and `uv run --directory backend ruff check app tests alembic` from the repository root.

Steps:
1. Record workspace last use — Alembic migration 0032 adds nullable `last_used_at` (timezone-aware) to `workspaces`; add the column to the model; stamp it (best-effort, never failing the turn) when `_build_coding_toolsets` in `backend/app/services/agent_session.py` attaches the workspace, through a repository function per `.claude/rules/architecture.md`.
2. Add the sandbox GC task — new `backend/app/worker/tasks/sandbox_tasks.py` with a daily-cron `@broker.task` that no-ops unless `ENABLE_CODING`; selects workspaces whose `last_used_at` (falling back to `created_at`) is older than a new `SANDBOX_STATE_TTL_DAYS` setting (default 7); calls sandboxd `DELETE /sessions/{root}?purge=true` with the service token for each; logs per-workspace outcomes and never touches the row. Register the module import at the bottom of `backend/app/worker/taskiq_app.py`.
3. Let the worker reach sandboxd — in `docker-compose.yml`, join `taskiq-worker` and `taskiq-scheduler` to `sandbox-internal` with a comment citing rule 8 (they currently cannot reach `http://sandboxd:8080`).
4. Test the GC task — registration is asserted by the existing import test pattern in `backend/tests/test_worker_taskiq.py`; add tests for TTL selection (idle vs fresh vs never-used), the purge call (HTTP mocked), the disabled no-op, and row survival.

## Phase 3: Per-conversation auto-approve activation

Goal: a stored `auto_approve=true` no longer grants anything by itself — write/execute auto-approval requires a per-turn activation flag, and every auto-approved call is stamped `auto_approved=true` on its tool span.
Validation: `uv run --directory backend pytest tests/test_coding_tools.py tests/test_workspaces.py -q` and `uv run --directory backend ruff check app tests` from the repository root.

Steps:
1. Gate auto-approval on per-turn activation — `process_message` in `backend/app/services/agent_session.py` reads a new optional `workspace_auto_approve` boolean from the turn payload (absent means false) and passes it into the coding toolkit build; `_auto_approved_tools` in `backend/app/agents/tools/coding.py` returns the write tools only when the stored preference AND the activation are both true (ruleset rules unchanged: strict still refuses, readonly has nothing to approve). The activation is an AND-gate — it can never widen what the stored preference allows.
2. Stamp auto-approved tool spans — following the `WrapperToolset` precedent in `backend/app/agents/google_loadout.py`, wrap the coding toolset so a call to an auto-approved write tool sets `auto_approved=true` on the current OpenTelemetry span (pydantic-ai's instrumentation owns the span; this only adds the attribute rule 9 names as the audit trail).
3. Test the activation matrix and span stamp — extend `backend/tests/test_coding_tools.py`: stored-preference × activation × ruleset matrix (notably: stored true + activation absent grants nothing), and the span attribute lands on auto-approved calls only.

## Phase 4: Chat-controls toggle and auto-approve surfacing

Goal: the user activates auto-approve per conversation from the chat controls, the active override is visible for the whole conversation, a new conversation starts unprivileged, and auto-approved calls are visible in the transcript.
Validation: `cd frontend && bun install && bun run lint && bun run type-check && bun run test:run`.

Steps:
1. Hold activation per conversation — `frontend/src/stores/chat-mode-store.ts` gains `autoApproveConversationId: string | null`, excluded from persistence so a reload or a different conversation starts unprivileged; selecting a different workspace or clearing the workspace clears it.
2. Add the chat-controls toggle — in the `WorkspacePicker` panel of `frontend/src/components/chat/chat-controls.tsx`, render a toggle only when the selected workspace has `auto_approve=true` and `ruleset === "default"`; it sets the activation for the current conversation; copy goes through `next-intl` messages; the existing explanatory text updates to describe per-conversation activation.
3. Show the active override and surface auto-approved calls — while activation is on for the current conversation, the chat controls show a visible active-override indicator (ADR-006 rule 4); `frontend/src/hooks/use-chat.ts` handles the until-now-unhandled `tool_auto_approved` WebSocket event and marks the affected tool calls as auto-approved in the transcript state.
4. Send activation with each turn — `doSend` in `use-chat.ts` includes `workspace_auto_approve: true` only when a workspace is named and the activation matches the current conversation.
5. Test the toggle, scoping, and event handling — vitest: store scoping (new conversation unprivileged, reload unprivileged), toggle render matrix (hidden for strict/readonly/no-preference), `tool_auto_approved` handling, and the payload field.
